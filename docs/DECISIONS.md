No design documents existed before 2026-10-13. Reasons below are reconstructed. Each is labelled:

- **Evidence** — what can be seen in files, benchmarks or the recorded integration brief.
- **Inference** — a plausible reason that nobody wrote down. Treat as a hypothesis.

Dates are file modification times on the reference machine unless stated otherwise.

| # | Decision | Since | Evidence | Inference | Open trade-offs |
|---|---|---|---|---|---|
| D1 | Chat answers come from a **local Ollama model**, `qwen3:1.7b`, prompted only in English | 2026-10-11 (`chat.py`) | Every prototype (`chat.py`, `chat_int8.py`, `chat_madlad.py`) and `server.py` call `localhost:11434` with `qwen3:1.7b`. `qwen3:4b` was pulled ≈ 30 min earlier than `1.7b` and is unused. | The smaller model was preferred for speed/memory on an 8 GB CPU-only machine; English-only prompting because small models answer best in English. | Answer quality vs. size; `qwen3-uz` / `qwen3-fast` custom tags exist in Ollama but their purpose is unrecorded. |
| D2 | Translation by **MADLAD-400 3B via CTranslate2 INT8**, replacing NLLB-200 | 2026-10-11/12 | Prototype sequence NLLB (transformers) → NLLB INT8 → MADLAD; `chat_int8_nllb_backup.py`; `benchmarks\comparison.csv` compares both on the same sentences: MADLAD ≈ 1.0–1.5 s vs NLLB ≈ 0.3–0.5 s per sentence, and e.g. NLLB renders "Salom, bugun qalaysan?" as "Hello, are you staying today?" while MADLAD gives "Hello, how are you today?". | MADLAD was chosen for better Uzbek quality despite being ≈ 3–4× slower and far larger. | Memory: `server.py` commits ≈ 9.9 GB — the main reason the full system does not fit. NLLB INT8 is 600 MB on disk. A quality/memory re-evaluation is open. |
| D3 | **Language detection by heuristic** inside the backend; client-supplied language ignored | by 2026-10-13 (`server.py`; backup named `server.py.before_auto_language.bak`) | Code. The backup differs from the current file in exactly one line: it used `lang = requested_language if requested_language in ("uz", "ru", "en") else detect_language(text)`; the current file always calls `detect_language(text)` (`VERIFIED` by diff). | "Auto language" was introduced so users need not pick a language; why the explicit choice was removed rather than kept alongside `auto` is not recorded. | Misdetection (K7–K9); selector now misleading. |
| D4 | **One process and one virtual environment per service** | 2026-10-12 onward | Four venvs with incompatible pins (`transformers` 4.57.6 vs 5.19.0, `huggingface_hub` 0.36 vs 2.2); the Kokoro integration brief (2026-10-13) explicitly required a new isolated `.venv-kokoro` and forbade touching `.venv` and `.venv-piper`; `README.txt` describes the Uzbek TTS as a "separate persistent service". | Isolation keeps a working component safe when another is added; a TTS crash cannot take down chat. | More memory (duplicated runtimes: torch in two envs, onnxruntime in three), four windows to manage, no orchestration. |
| D5 | **Uzbek speech from a fine-tuned VITS ONNX model** | 2026-10-12 | `README.txt` ("FINE-TUNED UZBEK ONNX TTS"), `tts_onnx_server.py`, model in `stt-tts-uz\models\`. Kokoro and the installed Piper voices have no Uzbek voice. | It was the available Uzbek voice of acceptable quality; ONNX Runtime keeps it light (≈ 0.5 s per sentence). | Provenance and license unknown; depends on unlicensed third-party text code; no number normalization. |
| D6 | **Piper** for Russian/English, now kept as **fallback** | 2026-10-12/13 | Voices downloaded 2026-10-12; server written 2026-10-13; the Kokoro brief required: do not remove the Piper mode, keep it as fallback. | First local replacement for browser voices; retained because it is light (no resident model) and independent of Kokoro's memory needs. | Slow per request (process spawn); GPL-3.0 tool; different voice timbre when fallback kicks in mid-conversation. |
| D7 | **Kokoro-82M `af_heart`** as the English voice | 2026-10-13 | Specified by the project owner in the integration brief (model `hexgrad/Kokoro-82M`, voice `af_heart`). | Preferred for naturalness over Piper `lessac`. No comparison was recorded. | ≈ 1.8 GB commit for one voice vs. ≈ 0 resident for Piper. |
| D8 | **Kokoro-RU `masha`** as the Russian voice (explicitly not `sveta`) | 2026-10-13 | Specified by the owner in the brief (model `zaakirio/kokoro-ru`, voice `masha`, "do not use `sveta`"). Upstream card: `masha` is brighter than `sveta` (−26.2 dB vs −33.8 dB in the 6–10 kHz band). | Voice preference; possibly the brightness difference.
